# Mixtape — Codebase Map

Mixtape is a Flask + SQLAlchemy REST API for a social music app: friends share
songs, rate them, build collaborative playlists, keep listening streaks, and see
what friends are playing. There's no frontend in this repo — every "feature" is a
JSON endpoint. The app follows a strict **route → service → model** layering, and
all five tracked bugs live in the service layer.

---

## The Files and What Each Actually Does

### `app.py` — application factory + DB bootstrap
Defines `create_app(config=None)`, the Flask factory. It configures a SQLite
database (`mixtape.db` by default, overridable via `DATABASE_URL`), initializes the
shared `db = SQLAlchemy()` object, and registers four blueprints under URL
prefixes: `/songs`, `/playlists`, `/users`, `/feed`. It also defines a `/` index
route that returns a map of available endpoints, and calls `db.create_all()` inside
an app context so the schema exists on startup. The module-level `db` object is the
single SQLAlchemy instance every other module imports — this is what ties models and
services together.

### `models.py` — the data model (5 entities + 3 association tables)
Defines all persistent state. Every primary key is a string UUID generated by
`generate_uuid()`. The entity models:

- **User** — `username`, `email`, plus two streak-tracking columns:
  `listening_streak` (int) and `last_listened_at` (datetime). Has a self-referential
  many-to-many `friends` relationship through the `friendships` table.
- **Song** — `title`, `artist`, `album`, `genre`, and `shared_by` (FK to the User
  who shared it — this is who gets notified about interactions). Tags hang off it
  via the `song_tags` association table.
- **ListeningEvent** — one row per "user played song at time". This is the raw
  signal behind both streaks and the feeds.
- **Rating** — a user's 1–5 `score` for a song. A `UniqueConstraint(user_id,
  song_id)` enforces one rating per user per song, so re-rating is an *update*, not a
  new row. Note: the rating is its own table, not a column on Song.
- **Notification** — `user_id` (recipient), `notification_type` (e.g.
  `"song_added_to_playlist"`, `"song_rated"`), `body` text, and a `read` flag.

The three association tables matter:

- **`friendships`** — symmetric many-to-many between users. Friendship is stored as
  *two* directed rows (seed inserts both `(u1→u2)` and `(u2→u1)`), so a one-directional
  insert would make a friendship invisible from one side.
- **`song_tags`** — plain many-to-many between songs and tags.
- **`playlist_entries`** — the important one. It's a many-to-many between playlists
  and songs **with extra columns**: `position` (explicit 1-based ordering — playlist
  order is deliberate, not insertion order), `added_by`, and `added_at`. Because of
  `position`, "the songs in a playlist" is an ordered query, not just a set.

### `routes/` — thin HTTP adapters
Four blueprints. Every route does the same three things and nothing more: parse
input from the request, call exactly one service function, and shape the JSON
response (including translating a service's `ValueError` into a 400/404). No
business logic lives here.

- **`routes/songs.py`** — `GET /songs/search?q=`, `GET /songs/<id>`,
  `POST /songs/<id>/rate`, `POST /songs/<id>/listen`. Note the cross-wiring: the
  *rate* route imports from `notification_service`, and the *listen* route imports
  from `streak_service` — the route names don't map one-to-one to service files.
- **`routes/playlists.py`** — create playlist, get playlist metadata, get a
  playlist's songs, and `POST /playlists/<id>/songs` to add a song. Adding a song
  goes through `notification_service.add_to_playlist`, not the playlist service —
  because adding a song is what *triggers a notification*.
- **`routes/users.py`** — get user, get streak, list notifications
  (`?unread_only=true`), and mark a notification read.
- **`routes/feed.py`** — `GET /feed/<user_id>/listening-now` and
  `GET /feed/<user_id>/activity`.

### `services/` — all the business logic (and all the bugs)
- **`streak_service.py`** — `record_listening_event` (creates the ListeningEvent
  and updates the streak) and the core `update_listening_streak`, which compares
  `last_listened_at.date()` to today and either increments, holds, or resets. Plus a
  read-only `get_streak`.
- **`feed_service.py`** — `get_friends_listening_now` (friends active within a
  recency window, deduped to one most-recent song per friend) and
  `get_activity_feed` (most recent N events from friends, no recency filter).
- **`search_service.py`** — `search_songs` (case-insensitive `ilike` match on title
  or artist, joined to tags) and `get_song`.
- **`notification_service.py`** — the hub for user-to-user interactions:
  `create_notification` (the low-level writer), `add_to_playlist` (adds a song *and*
  notifies the sharer), `rate_song` (upserts a Rating), plus `get_notifications` and
  `mark_as_read`.
- **`playlist_service.py`** — `create_playlist`, `get_playlist_songs` (ordered by
  `position`), `get_playlist`, `get_user_playlists`.

### `seed_data.py` — deterministic test fixtures
Drops and recreates all tables, then inserts 5 users (nova, darius, simone, kenji,
aaliya) with established bidirectional friendships, songs deliberately split into
0-tag / 1-tag / 3+-tag buckets, 3 playlists, and listening events split into "recent
(last ~30 min)" and "old (1–14 days)" sets. The seed data is purpose-built to expose
the bugs — e.g. the 3+-tag songs surface the search duplication, and the recent-vs-old
event split surfaces the feed recency problem.

### `tests/` — `test_streaks.py`, `test_search.py`, `test_playlists.py`
Unit tests against three of the five buggy services.

## Data Flow #1 — A user adds a friend's song to a playlist → sharer gets notified

This is the "sharing triggers a notification" flow.

1. **HTTP** — `POST /playlists/<playlist_id>/songs` with JSON
   `{"song_id": ..., "added_by": ...}`.
2. **Route** — [routes/playlists.py:43](routes/playlists.py#L43) `add_song()` parses
   `song_id` and `added_by`, rejects missing fields with a 400, then calls
   `add_to_playlist(playlist_id, song_id, added_by)`.
3. **Service** — [services/notification_service.py:35](services/notification_service.py#L35)
   `add_to_playlist`:
   - Loads the Song, the adding User, and the Playlist; raises `ValueError` (→ 400)
     if any is missing.
   - Appends the song to `playlist.songs` (which writes a `playlist_entries` row) if
     it isn't already present, and commits.
   - **The notification branch:** if `song.shared_by != added_by_user_id` (i.e. you
     didn't add your own song), it calls `create_notification(...)` targeting
     `song.shared_by` — the *original sharer*, not the playlist owner — with type
     `"song_added_to_playlist"`.
4. **Notification write** — [services/notification_service.py:13](services/notification_service.py#L13)
   `create_notification` inserts a `Notification` row and commits.
5. **Read side (later)** — the sharer calls `GET /users/<id>/notifications` →
   [routes/users.py:29](routes/users.py#L29) → `get_notifications` →
   queries Notifications for that user, newest first, returns dicts.

So a "share" never directly creates a Notification — the notification is a
*side effect of another user interacting with* the shared song, and it's always
routed to `Song.shared_by`.

## Data Flow #2 — A user listens to a song → streak updates

This shows the route/service cross-wiring and the streak logic.

1. **HTTP** — `POST /songs/<song_id>/listen` with `{"user_id": ...}`.
2. **Route** — [routes/songs.py:43](routes/songs.py#L43) `listen()` validates
   `user_id`, then calls `record_listening_event(user_id, song_id)` — note this lives
   in **`streak_service`**, not a "song service".
3. **Service** — [services/streak_service.py:14](services/streak_service.py#L14)
   `record_listening_event` loads the user (404 if missing), creates a
   `ListeningEvent` at `now`, then calls `update_listening_streak(user, now)`.
4. **Streak math** — [services/streak_service.py:42](services/streak_service.py#L42)
   compares `last_listened_at.date()` to `today`: never-listened → streak = 1; same
   day → no change; exactly one day ago → increment; otherwise → reset to 1. It also
   normalizes naive datetimes to UTC before comparing.
5. **Commit** — both the event and the mutated `user.listening_streak` /
   `last_listened_at` are committed in one transaction. The same `ListeningEvent`
   rows are later read back by `feed_service` for the "listening now" and activity
   feeds — one write, two readers.

## Patterns I Noticed

- **Strict three-layer architecture.** Routes are deliberately dumb (parse →
  delegate → format); services own all logic and DB access; models are pure schema.
  Every route delegates to exactly one service call.
- **Errors flow via `ValueError`.** Services raise `ValueError("X not found")`;
  routes catch it and map to 404 (reads) or 400 (writes). There's no custom
  exception hierarchy — the string message becomes the JSON `error`.
- **Routes are organized by HTTP resource, services by domain concept — and they
  don't line up 1:1.** The `/songs/.../listen` route reaches into `streak_service`;
  the `/playlists/.../songs` POST reaches into `notification_service`. To trace a bug
  you have to follow the import, not assume the filename.
- **Notifications are always addressed to the content owner.** Both interaction
  paths resolve the recipient as `Song.shared_by`, with an explicit "don't notify
  yourself" guard.
- **`db.session.get(Model, id)` everywhere, with a not-found guard before use.**
  Single-entity lookups are uniform; list queries use the explicit query builder.
- **Ordering is explicit and intentional.** Playlists order by the
  `playlist_entries.position` column; feeds order by `listened_at desc`. Nothing
  relies on insertion/row order.
- **The seed data is adversarial by design.** Each fixture bucket (multi-tag songs,
  recent-vs-old events, yesterday/today `last_listened_at` values) is constructed to
  trip a specific one of the five open bugs, so the data doubles as a reproduction
  harness.

## Where the Five Bugs Live (from tracing the above)

| # | Symptom | Service | What the trace points at |
|---|---------|---------|--------------------------|
| 1 | Streak keeps resetting | `streak_service.py` | `update_listening_streak` increments only `if days_since_last == 1 and today.weekday() != 6` — a Sunday-specific guard that resets an otherwise-valid streak. |
| 2 | "Listening Now" shows people from yesterday | `feed_service.py` | `RECENT_THRESHOLD = timedelta(hours=24)` — far wider than the "now" window the seed data (~30 min) expects. |
| 3 | Same song appears twice in search | `search_service.py` | `outerjoin(song_tags)` multiplies rows per tag and the query never de-duplicates, so 3+-tag songs repeat. |
| 4 | No notification when a friend rates my song | `notification_service.py` | `rate_song` upserts the Rating but never calls `create_notification`, unlike `add_to_playlist`. |
| 5 | Last song in a playlist never shows | `playlist_service.py` | `get_playlist_songs` returns `songs[:-1]`, dropping the final ordered entry. |

## How I Reproduced Bugs 1–3

I verified each of these against the real code path (not just by reading it), using
`python seed_data.py` for app state plus a few small probe scripts. Environment:
SQLAlchemy **2.0.51**, Flask-SQLAlchemy, SQLite. The headline finding: **bugs 2 and 3
only surface under specific data conditions** — the default seed data actually *masks*
both of them, which is why their existing unit tests can pass while real users still
hit the bug.

### Bug 1 — Streak keeps resetting

- **Trigger condition:** the *consecutive* listen (the one that should bump the
  streak) lands on a **Sunday**. The check `days_since_last == 1 and today.weekday() != 6`
  treats Sunday (`weekday() == 6`) as never-incrementable, so it falls through to the
  `else` and resets the streak to 1.
- **How I reproduced it:** called `update_listening_streak(user, day)` twice in a row.
  - Saturday `2024-06-15` then Sunday `2024-06-16` → streak went `1 → 1` (expected `2`). **Reproduced.**
  - As a control, Wednesday → Thursday (no Sunday involved) → streak went `1 → 2` correctly.
- **Also confirmed by the existing suite:** `tests/test_streaks.py::test_streak_increments_on_sunday`
  fails with `assert 1 == 2`. This bug is *not* data-condition-masked — any user whose
  streak ticks over on a Sunday loses it.

### Bug 2 — "Friends Listening Now" shows people from yesterday

- **Root cause:** `RECENT_THRESHOLD = timedelta(hours=24)`, so the cutoff admits
  anything from the last 24 hours into a feed that should mean "right now."
- **Why the default seed hides it (the specific condition):** `get_friends_listening_now`
  dedupes to the *most recent event per friend*. In the seed, every one of nova's
  friends (darius, simone, kenji) also has a fresh ~10–20-min-old event, so the fresh
  event wins the dedup and the stale-but-<24h events never get a chance to show. Running
  the feed for nova as-seeded shows only the three fresh entries — the bug looks absent.
- **The condition needed to see it:** a friend whose *most recent* listen is between
  ~30 minutes and 24 hours ago (i.e. no fresher event to mask it).
- **How I reproduced it:** for nova's friend darius, I deleted his fresh events and
  inserted a single listen **6 hours ago**, then called `get_friends_listening_now(nova.id)`.
  darius appeared in "Listening NOW" with `age=6:00:00`. **Reproduced** — a 6-hour-old
  listen should never count as "now."

### Bug 3 — Same song shows up twice in search

- **Root cause:** `search_songs` does `outerjoin(song_tags, ...)` and never
  de-duplicates, so the SQL result has **one row per tag** for each matching song.
- **Specific conditions required (two of them):**
  1. **Data condition:** the matching song must have **2+ tags**. Zero-tag and
     one-tag songs produce ≤1 join row and can *never* duplicate — only the multi-tag
     songs (e.g. "Crown Heights Anthem", 3 tags) fan out.
  2. **Version/ORM condition:** the duplication is **latent in this codebase**. The
     service uses the *legacy* `db.session.query(Song).all()` API, which on
     SQLAlchemy 2.0.51 silently uniquifies entities by identity — collapsing the fanned-out
     rows back to one. So through `GET /songs/search`, the duplicate does **not** appear
     here, and `tests/test_search.py::test_search_no_duplicates_multi_tag_song` passes.
- **How I reproduced (proving the fan-out is real even though it's masked):** for the
  query `"Crown"` (matches the single 3-tag song):
  - Raw join selecting `Song.id`: **3 rows.**
  - `select(Song).scalars().all()` (the 2.0-style API, no `.unique()`): **3 Song objects** — duplicated.
  - `db.session.query(Song).all()` (what the service uses): **1 object** — masked by legacy uniquing.
  The defect is one missing `.distinct()` / `.unique()`; it stays hidden only as long as
  the code keeps using legacy `Query` and a backend that uniquifies. Port the same query
  to the 2.0 `select()` style (or add a second join that defeats identity uniquing) and
  every 2+-tag song immediately returns N copies.

## Root Cause Analysis — Bug 1: "My listening streak keeps resetting"

**Issue #1 — My listening streak keeps resetting** (`streak_service.py`)

### How I reproduced it
Before touching any code I drove the streak logic directly, the same way the
`POST /songs/<id>/listen` route does (route → `record_listening_event` →
`update_listening_streak`). I called `update_listening_streak(user, day)` for two
consecutive calendar days and read back `user.listening_streak`:

- **Saturday 2024-06-15 → Sunday 2024-06-16:** streak went `1 → 1`. A second
  consecutive day should make it `2`. **Bug confirmed.**
- **Control, Wednesday → Thursday:** streak went `1 → 2` correctly.

The existing suite agreed: `tests/test_streaks.py::test_streak_increments_on_sunday`
failed with `assert 1 == 2`. So the trigger condition is precise: *the day that should
extend the streak falls on a Sunday.* Every other consecutive-day pair worked.

### How I found the root cause
The README maps the symptom to `streak_service.py`, so I traced the listen flow:
[routes/songs.py:43](routes/songs.py#L43) `listen()` → `record_listening_event`
([services/streak_service.py:14](services/streak_service.py#L14)) → `update_listening_streak`
([services/streak_service.py:42](services/streak_service.py#L42)). The first three
branches read fine — new user → 1, same day → no-op, `days_since_last == 1` →
increment. The moment of confidence was the increment branch's guard:

```python
elif days_since_last == 1 and today.weekday() != 6:
    user.listening_streak += 1
else:
    user.listening_streak = 1
```

That extra `and today.weekday() != 6` is the only thing in the function that singles
out one weekday. Since my reproduction failed *only* when the second listen landed on
a Sunday, and `datetime.weekday()` returns `6` for Sunday, this clause exactly
accounts for the observed behavior — not just a suspicious area, but the specific
condition: a genuine consecutive-day listen on a Sunday skips the `+= 1` and falls
through to the `else`, resetting the streak to 1.

### The root cause
`datetime.weekday()` returns `6` for Sunday. The increment branch required both
`days_since_last == 1` (the listen really is on the next calendar day) **and**
`today.weekday() != 6`. So whenever the qualifying next-day listen happened on a
Sunday, the `and` short-circuited to `False`, the increment was skipped, and control
fell into the `else: user.listening_streak = 1` branch — silently resetting a streak
that should have grown. The streak therefore could never survive into a Sunday, which
presents to the user as "my streak keeps resetting." The day-difference math
(`days_since_last`) was already correct and weekday-agnostic; the weekday term was an
unnecessary, incorrect extra condition with no place in a "consecutive calendar day"
rule.

### My fix and side-effect check
One-line, root-cause-targeted change in
[services/streak_service.py:73](services/streak_service.py#L73) — drop the spurious
weekday term so any single-day gap increments:

```python
elif days_since_last == 1:
    user.listening_streak += 1
```

This fixes the root cause because the streak rule depends only on how many calendar
days have elapsed (`days_since_last`), which the code already computes correctly; the
weekday of that day is irrelevant. I changed nothing else — `days_since_last == 0`
(same-day) and the `else` (gap ≥ 2 days) branches are untouched.

**Boundary check (both sides of the Sunday boundary):**

| Scenario | Result | Expected |
|---|---|---|
| Sat → Sun (consecutive, lands on Sunday) | 2 | 2 ✅ |
| Sun → Mon (consecutive, leaves Sunday) | 3 | 3 ✅ |
| Wed → Thu (consecutive, no Sunday) | 2 | 2 ✅ |
| Sun → Sun (same day, twice) | 1 | 1 ✅ (no double-count) |
| Fri → Sun (skips Saturday) | 1 | 1 ✅ (still resets) |
| New user, first listen | 1 | 1 ✅ |

**Related functionality checked:** I looked at everything touching the same data. The
same-day branch still prevents double-counting (including on Sundays); the gap-≥-2
reset still fires across a Sunday (Fri→Sun resets correctly), so I didn't trade the
under-reset bug for an over-counting one. `record_listening_event` (the only caller)
and `get_streak` (read-only) don't depend on weekday, so they're unaffected. Full
suite: `tests/test_streaks.py` now passes entirely (including the previously failing
Sunday test); the only remaining failures are the two `test_playlists.py` cases, which
are the separate, unaddressed Issue #5.

## Root Cause Analysis — Bug 2: "Friends Listening Now shows people from yesterday"

**Issue #2 — Friends Listening Now shows people from yesterday** (`feed_service.py`)

### How I reproduced it
The feature is `GET /feed/<user_id>/listening-now` → `get_friends_listening_now`
([services/feed_service.py:16](services/feed_service.py#L16)). I exercised it against
seeded data (`python seed_data.py`) for `nova`.

The default seed *masks* the bug: every one of nova's friends (darius, simone, kenji)
also has a fresh ~10–20-min-old event, and the function dedupes to the most-recent
event per friend, so the fresh event always wins and the stale ones never show. So the
condition needed to actually see it is **a friend whose most-recent listen is between
~30 minutes and 24 hours ago, with no fresher event to mask it.**

I constructed exactly that: for nova's friend darius I deleted his fresh events and
inserted a single listen **6 hours ago**, then called `get_friends_listening_now(nova.id)`.
darius appeared in "Listening NOW" with `age=6:00:00`. **Bug confirmed** — a 6-hour-old
listen should never count as "now."

### How I found the root cause
The README maps the symptom to `feed_service.py`. I traced
[routes/feed.py:9](routes/feed.py#L9) `listening_now()` → `get_friends_listening_now`.
The query itself is correct — it filters `ListeningEvent.listened_at >= cutoff` and
orders by most-recent. The only thing that defines "recent" is the module constant
feeding that cutoff:

```python
RECENT_THRESHOLD = timedelta(hours=24)
...
cutoff = datetime.now(timezone.utc) - RECENT_THRESHOLD
```

The moment of confidence: the seed file documents the intended contract right next to
the data it creates — *"Recent events (within the past 30 minutes) — should appear in
'listening now'"* and *"Older events (1–14 days ago) — should NOT appear in 'listening
now' after fix."* A 24-hour window is ~48× wider than that intended ~30-minute "now"
window, which exactly explains why a friend who listened hours ago (but within a day)
still shows up. Not a suspicious area — the single constant *is* the cutoff, and its
value is the defect.

### The root cause
"Listening Now" is supposed to mean *currently/just-now listening* — a window of
roughly 30 minutes. But `RECENT_THRESHOLD` was set to `timedelta(hours=24)`, so the
recency filter `listened_at >= now - RECENT_THRESHOLD` admitted **any event from the
last full day**. Any friend who listened to something earlier today — or even
yesterday evening, up to 24 hours back — was treated as "listening now." The query
logic, ordering, and per-friend dedup were all correct; the sole problem was the
threshold value being far larger than the feature's definition of "now."

### My fix and side-effect check
One-line, root-cause-targeted change in
[services/feed_service.py:13](services/feed_service.py#L13) — narrow the window to the
~30-minute "now" the feature (and the seed contract) intends:

```python
RECENT_THRESHOLD = timedelta(minutes=30)
```

Nothing else changed — the query, the cutoff computation, and the dedup logic that
consume the constant were already correct.

**Boundary check (both sides of the 30-minute cutoff):**

| Scenario | Shown in "Listening Now"? | Expected |
|---|---|---|
| Friend listened 10–20 min ago (seed) | yes | yes ✅ |
| Friend listened 29 min ago | yes | yes ✅ |
| Friend listened 31 min ago | no | no ✅ |
| Friend listened 6 h ago (bug repro) | no | no ✅ |

**Related functionality checked:** I looked at the other consumer of the same
data/feature, `get_activity_feed` ([services/feed_service.py:65](services/feed_service.py#L65)).
By design it is *not* filtered by recency (its docstring says so) and it does **not**
reference `RECENT_THRESHOLD`, so the change can't affect it — I confirmed the activity
feed still returns the older (>30 min) events after the fix. The per-friend dedup in
`listening-now` is unchanged, so friends with a genuinely fresh event still appear
exactly once. Full suite is unchanged at 11 passed; the only failures remain the two
`test_playlists.py` cases for the separate Issue #5. (There is no dedicated feed test
in the suite, so I verified this bug via the probe scenarios above.)

## Root Cause Analysis — Bug 3: "The same song keeps showing up twice in search"

**Issue #3 — The same song keeps showing up twice in search** (`search_service.py`)

### How I reproduced it
The feature is `GET /songs/search?q=<query>` → `search_songs`
([services/search_service.py:11](services/search_service.py#L11)). I seeded the app
(`python seed_data.py`, which creates songs with 0, 1, and 3+ tags) and searched for
the 3-tag song "Crown Heights Anthem" via `q="Crown"`.

This bug only appears under **two simultaneous conditions**:
1. **Data condition:** the matching song must have **2+ tags**. 0-tag and 1-tag songs
   produce ≤1 joined row and can never duplicate — only multi-tag songs fan out.
2. **ORM condition:** the duplication is **latent** in this codebase. The service used
   the *legacy* `db.session.query(Song).all()` API, which on SQLAlchemy 2.0.51 silently
   uniquifies entities by identity, collapsing the fanned-out rows back to one. So
   through `GET /songs/search` the duplicate did **not** surface here, which is why
   `tests/test_search.py::test_search_no_duplicates_multi_tag_song` passes as-is.

To prove the defect was real rather than imagined, I measured the query *underneath*
the masking. For `q="Crown"` (the single 3-tag song):
- raw join selecting `Song.id` → **3 rows**
- `select(Song).scalars().all()` (the 2.0-style API, no `.unique()`) → **3 Song objects**
- `db.session.query(Song).all()` (what the service used) → **1 object** (masked)

So the fan-out genuinely existed; it was one driver/ORM detail away from being visible.

### How I found the root cause
The README maps the symptom to `search_service.py`. I read the single query in
`search_songs` and the model layer it touches. The query joins `song_tags`:

```python
db.session.query(Song)
  .outerjoin(song_tags, Song.id == song_tags.c.song_id)
  .filter(or_(Song.title.ilike(...), Song.artist.ilike(...)))
```

The moment of confidence came from asking *what the join is actually for.* The
`filter` only references `Song.title` and `Song.artist` — never any `song_tags` or
`Tag` column. And `to_dict()` ([models.py:92](models.py#L92)) builds the `tags` list
from `self.tags`, a `lazy="subquery"` relationship ([models.py:90](models.py#L90))
that issues its own query — it does not read from this join at all. So the join
contributes **nothing** to either the filter or the output; its only effect is to emit
one result row per `(song, tag)` pair. That pinpointed the exact cause: a row fan-out
from an unnecessary join, with no de-duplication.

### The root cause
`song_tags` is a many-to-many association table — one row per (song, tag) pair. The
query `outerjoin`ed it but never used any of its columns for filtering or selection.
Because a SQL join over a one-to-many produces the cartesian expansion, a song with N
tags yielded **N duplicate result rows** (the 3-tag song → 3 rows), and the query
applied no `DISTINCT`. In other words, the bug is a join that should never have been
in the query: it can only multiply rows, never change which songs match. (The reason
end users could still hit it despite the legacy-`Query` masking is that the underlying
result set was genuinely duplicated — any move to the modern `select()` API, or a
backend/path that doesn't uniquify by identity, exposes it immediately.)

### My fix and side-effect check
The targeted fix removes the root cause at its source — the unnecessary join — rather
than masking the symptom with `.distinct()` on a join that shouldn't exist
([services/search_service.py:25](services/search_service.py#L25)):

```python
results = (
    db.session.query(Song)
    .filter(
        db.or_(
            Song.title.ilike(f"%{query}%"),
            Song.artist.ilike(f"%{query}%"),
        )
    )
    .all()
)
```

I also dropped the now-unused `song_tags` import
([services/search_service.py:8](services/search_service.py#L8)). That is the only
other change, and it is necessary purely to avoid leaving a dead import behind — no
logic depends on it. With the join gone the SQL returns one row per matching song by
construction, so correctness no longer relies on the ORM happening to uniquify.

I verified the fan-out is fixed *below* the masking layer: the raw query for `q="Crown"`
now returns **1 row** (was 3).
